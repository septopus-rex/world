# Septopus World (世界) 协议

在 **Septopus 引擎** 中，“世界 (`world`)”是最高级别的管理和物理边界框。一个 Septopus 世界由若干连续的地块 (Blocks) 网格组成，并由引擎强制执行全局物理、大气条件和访问规则。地块内的内容组织（如通过 SPP 协议）则是该管理框架下的具体实现。

## 1. 世界架构与布局 (World Architecture & Layout)

Septopus 元宇宙由固定数量的顶层世界组成。
*   **世界总数**: 96 个独立的世界。**这是元宇宙级常量**（属于宇宙立方体，不属于任何单个世界），不在世界文档里。
*   **宏观结构**: 这 96 个世界在数学上被映射到一个巨大宇宙立方体的 6 个面上（每个面 4x4 个世界）。

**世界几何（`range` / `block` / `diff`）是世界自己的配置数据（规范，2026-07-27 修订）**——由**世界文档**声明，不是引擎常量：

| 字段 | 含义 | 协议默认值（文档未声明时） |
|---|---|---|
| `world.range` | 世界网格的地块数 `[东, 北]`，地块编号从 `[1,1]` 起 | `[4096, 4096]` |
| `world.block` | 单个地块的尺寸（米），Septopus 轴序 `[东, 北, 高]` | `[16, 16, 16]` |
| `world.diff` | 高度粒度（米） | `0.1` |

**引擎实现必须从世界文档读取这三个值，不得把它们写死在代码里。** 参考世界（创世世界）声明的正是上表的默认值——所以「4096×4096 的 16 米地块」在实践中仍是绝大多数世界的形态；但那是**数据的取值**，不是**机制的约束**。

> **为什么改（推翻 2026-07-09 基础数据审计 D6「协议不变量、不可覆盖」的裁定）**：链上的世界配置管理需要能定义一个世界的网格；把这三个数钉死在引擎里，等于让「世界配置」这件事永远缺一块。同时，把值从常量搬进文档，也顺手消灭了参考实现里一个真实缺陷——块尺寸曾被存进一个**进程级可变静态**，多个世界同时存在时（测试、地块预览、风格包编辑器）会互相覆盖，后构造的赢。
>
> **合法性边界（非语义，防御损坏/恶意文档）**：`range` 每轴为 `1..1048576` 的整数；`block` 每轴为 `0.01..1024` 米；`diff` 为正数且不大于地块高度。越界的值由实现回退到上表默认值并上报，**不得静默接受**。

*   **横向两轴分别计算**：`range` 与 `block` 的东西/南北分量互相独立，世界网格**不必是正方形**，地块也不必。实现里用同一个数去乘两个轴是错误（参考实现曾犯过）。

## 2. 管理与“领主” (Administration & The "Lord")

每个世界都属于一个“领主 (Lord)”拥有的独立主权领地。领主持有管理用的 NFT 或加密密钥，该身份授予其在区块链上修改该世界全局参数的权限。

**领主权限 (Lord Capabilities):**
*   **商业化与税收**: 领主可以制定经济政策或将领主头衔出售/转让给另一个实体。
*   **美学覆盖 (Aesthetic Overrides)**: 领主可以更改未被占有的荒野地块的默认地形纹理、默认地面颜色和基础海拔。
*   **访问控制 (Access Control)**: 领主决定允许哪些操作模式（例如，禁止“幽灵 (Ghost)”旁观者或强制开启纯“游戏专用 (Game-Only)”场景）。

## 3. 全局生态系统配置 (Global Ecosystem Configurations)

各个世界共享一组基础物理定律（不可变数据 / Immutable Data），但允许领主调整特定的大气表盘（可变数据 / Mutable Data）。

### 不可变配置 (系统级 / System Level)
在 Septopus 引擎初始创世时设定，无法由个别领主更改。
- **时间膨胀 (Time Dilation)**: 例如，Septopus 时间与现实世界时间的比率（默认为快 20 倍）。
- **天体系统 (Celestial Bodies)**: 标准化的天空盒配置（1 个太阳，3 个月亮）。
- **世界总数**: 96（宇宙立方体 6 面 × 4×4）。

> **地块网格不再列在这里**（2026-07-27）：`range`/`block`/`diff` 已移入 §1 的「世界几何」，属**领主级可变配置**，由世界文档声明。上表 `1..1048576` 块 / `0.01..1024` 米的边界是**实现的防御性上限**（防止损坏文档产生 NaN 坐标或超大分配），不是领主可以调节的旋钮语义。

### 3.1 时间与天气的确定性推导（规范 / Normative）

> 「数据即逻辑」：世界的**历法**（年/月/日）与天气由**链高度 + 链 hash** 纯函数推导，
> 任何引擎（TS / UE）对同一输入必须得出**同一个日历日期、同一场雨**。时/分/秒（一天
> 之内具体几点）明确**不在**此契约内——见下方"历法/日内时间边界"说明与 §3.2。
> 实现参照 `engine/src/core/systems/EnvironmentSystem.ts`。

**输入**：`height`（链块高度）、`hash`（`0x` 前缀十六进制串，长度 ≥ 20）、`interval`（链出块间隔，秒）、
`epoch`（创世起始高度，默认 0）、`speed`（时间流速倍率，默认 1.0）。

**世界历法**（固定单位，只到"日"这一级，不含时/分/秒）：
```
elapsed = max(0, height − epoch) × interval × speed        （秒）
year  = elapsed ÷ 31104000（= 360 天），取余后依次：
month = ÷ 2592000（= 30 天） · day = ÷ 86400（余数丢弃）
```
每级**无条件赋值**（跨年边界时月/日必须归零，不得保留旧值）。

**天气**（hash 切片，字符位置按**去掉 `0x` 前缀后**计，0 起）：
```
category = parseInt(hash[10..11], 16) mod 4  →  0 clear · 1 cloud · 2 rain · 3 snow
grade    = parseInt(hash[12..13], 16) mod 4  →  0..3（强度梯度）
```
切片解析失败按 0 处理。**雷暴判定**：`category == rain 且 grade ≥ 1`。

**语义 / 渲染边界**：`(年, 月, 日, category, grade, 雷暴判定)` 是**语义**（跨引擎必须
一致）；太阳角度、光照强度、闪电闪光包络、粒子密度等是**渲染器自定义**（行为等效
即可，参照 adjunct 协议 §6 的「same effect」边界）。

**历法/日内时间边界（2026-07-13）**：时/分/秒**完全不从**链高度/hash 推导——它们是
一个本地的、不依赖链的客户端模拟（一个持续推进的"日内时钟"，`localDaySeconds` 秒
走完一个完整周期，见 §3.2）。原因：按 §3.2"一个比特币区块=一天"的约定，`interval`
是一天的整数倍，如果时/分/秒也走同一套公式，算出来永远是零——太阳会冻结在固定的
某一点，只在区块到来时跳一下，日夜流转就没有意义了。这样拆开之后，日历日期仍然
链上可验证（语义），而太阳的运行则连续、独立（属于氛围，非语义——跟太阳角度/光照
强度这条既有的"渲染器自定义"边界是同一条线，只是把时/分/秒这几个数字本身也划进
去了）。

### 3.2 参考链绑定：比特币（规范 / Normative）

§3.1 的公式本身链无关（设计如此），但具体某个世界必须绑定**一条**具体的链，才能让
所有引擎推导出同一份历法。参考客户端绑定的是**比特币**：`height`/`hash` 取自
当前链尖的区块高度与区块哈希，任何比特币轻客户端或公共浏览器都能读到（无需账户、
无需 RPC key、无需智能合约——纯公共数据）。原因：比特币已经是本项目启动期内容
版本锚定所用的链（`protocol/cn|en/boot-chain.md` 的 `{p,name,version,cid}` 锚）——
只依赖一条外部链，不是两条；且它的哈希是无需许可、极难操纵的公共随机源。

**约定：一个比特币区块 = 一个 Septopus 日。**
```
interval = 86400   （每个区块对应的 Septopus 世界时间，单位秒）
speed    = 1.0     （引擎默认值——桶 B，见 §9，不改）
epoch    = <世界创世时的比特币高度，由领主在上线时选定>
```
比特币真实的出块节奏（平均约 600 秒/块，每 2016 块调一次难度以维持这个平均值——
单个区块可能几秒也可能超过一小时）**不会**被当作逐块测量值接入：两个客户端看到
同一个 `(height, hash)`，不论那个区块实际挖了多久，都必须推出同一个日历日期，
所以 `interval` 用上面这个固定的协议常数，永远不用实测间隔。参考实现：
`client/core/src/lib/loader/BtcClock.ts`（以约 60 秒节奏轮询公共 Esplora 兼容
浏览器；区块实际约每 10 分钟才来一个，所以大多数轮询看不到高度变化——这是预期
行为，不是 bug；参考实现用 `VITE_BTC_CLOCK` 开关决定是否启用它）。没有真实网络的
开发/演示构建用一个合成的假计时器代替
（`EnvClock.ts`，dev/e2e 默认走这条），以快得多、随意选定的节奏推进**历法**（日期计数），方便调试
时看得清楚——这个假计时器**不属于**本规范绑定的一部分，它从不声称自己代表真实的
比特币状态。注意：BtcClock 和 EnvClock 二选一只影响**历法**（日期数字）推进的
快慢，按 §3.1，太阳的时/分/秒从来不由这两个时钟中的任何一个驱动，所以不管走哪条
路径，日夜流转的观感都完全一样（见下方"日内节奏默认值"）。

**日内节奏默认值**：`localDaySeconds = 600`（一个完整日内循环耗时 10 现实分钟，
`GlobalConfig.time.localDaySeconds`）——选它是因为大致贴近比特币自身的平均出块
间隔，让"太阳转一圈"和"日历跳一天"这两件事在体感上像是互相配合的节奏，尽管
按 §3.1 二者机制上完全独立，从不强制同步。世界文档的 `time` 段可以像覆盖
`speed`/`epoch` 一样覆盖它。

### 可变配置 (领主级 / Lord Level)
存储在智能合约中，可由世界的领主进行配置。
```json
{
    "world": {     
        "nickname": "Neon Genesis",        
        "mode": ["ghost", "normal", "game"],     
        "accuracy": 1000,
        "range": [4096, 4096],
        "block": [16, 16, 16],
        "diff": 0.1
    },
    "block": {     
        "elevation": 0,       
        "max": 30,            
        "color": 0x10b981,     
        "texture": 2          
    },
    "player": {
        "start": {
            "block": [2025, 619],   
            "position": [8, 8, 0],   
            "rotation": [0, 0, 0]   
        }
    }
}
```

### 配置层级 (Configuration Hierarchy)
1.  **Septopus 引擎核心配置 (Engine Core Config)**: 引擎不可变的基石铁律，**以及世界文档缺省时的协议默认值**（§1 的几何默认值、§9 桶 B 那张表）。这一层是**兜底**，不是**读取点**——引擎必须优先读世界文档。
2.  **世界配置**: 领主自定义的统一环境，**含 §1 的世界几何**。
3.  **Avatar/地块配置**: 个体玩家或地主本地化的数据覆盖。

## 5. 坐标与旋转契约(规范 / Normative)

任何引擎实现必须遵守下列坐标语义,否则同一份数据会解出朝向/位置不同的世界。

### 5.1 轴序

- **Septopus(数据)轴序**:`X 东 · Y 北 · Z 高`,单位米;地块内坐标相对地块**西南角**原点,
  地块编号 `[bx, by]` 从 `[1,1]` 起,上界为该世界声明的 `world.range`(§1;参考世界 4096×4096)。
- **块偏移按轴分别算**:引擎绝对坐标 = `(bx−1) × block[0] + 东` / `(by−1) × block[1] + 北`。
  两个横向轴各用**自己**的地块尺寸——网格与地块都不必是正方形。
- 引擎内部轴序自便(参考实现为 Three.js 的 X右/Y上/Z前,北 = −Z),但**数据一律
  以 Septopus 轴序书写与存储**,装载/持久化时由实现转换。

### 5.2 旋转(欧拉序与坐标系)

- 附属物 `[rx, ry, rz]`:**弧度,引擎系 Euler XYZ 序,绕几何中心**。它**不经**
  朝向换算直接在引擎系应用——即**绕竖直轴的 yaw 在 index 1**(engine Y = 上)。
- 由此存在一个刻意的不对称:**位置按 Septopus 系书写,旋转按引擎系书写**。创作内容时
  以此为准;新引擎实现时把 `[rx,ry,rz]` 当作"X右/Y上/Z前右手系的 XYZ 欧拉角、
  绕中心应用"即可对齐(观感等价,非逐位)。
- **玩家朝向(heading)例外**:玩家 yaw 采用导航语义(0 = 朝北,顺时针增,即罗盘
  heading),与引擎 yaw 的换算固定为 `heading = −engineYaw`。只有玩家出生/持久化
  朝向走此换算;附属物旋转不走。

### 5.3 尺寸

`size` 一律为**全长包围盒**(非半长),Septopus 轴序 `[东西, 南北, 高]`;
特例(a6 cone、a7 ball 直径语义)见 [adjunct-types.md](adjunct-types.md)。

## 9. 引擎常量分桶(规范,2026-07-09)

引擎实现中的常量按三桶归置(基础数据审计 P9/D6,**2026-07-27 修订**):

**协议不变量**(所有世界共享、不可覆盖):**世界数 96**。仅此一项——它属于宇宙立方体
而不属于任何单个世界。

> **世界网格与块尺寸已移出本桶**(原文为「4096×4096 块、块 16×16×16 m、高度粒度 0.1 m
> 不可覆盖」)。它们现在是**世界文档声明的可变配置**,见 §1 的「世界几何」表;其取值
> 仍然默认为 4096×4096 / 16 m / 0.1 m,但**引擎必须从文档读取,不得硬编码**。
> 起因:链上世界配置管理需要能定义一个世界的网格。

**协议默认值(桶 B)**——数据缺省时各引擎必须取同一值:

| 量 | 默认 | 世界数据覆盖点 |
|---|---|---|
| 重力 | **−19.62 m/s²**(刻意 2× 标准重力的手感值,协议如此钉定) | `player.capacity.gravityMultiplier`(乘数) |
| 玩家血量 | 100/100 | `player.capacity.maxHp` |
| 交互够得着距离 | **3.5 m**(玩家→命中点,非相机;编辑模式不限) | `player.capacity.reach` |
| 世界网格 | `[4096, 4096]` 块 | `world.range`(§1) |
| 地块尺寸 | `[16, 16, 16]` m,Septopus 轴序 | `world.block`(§1) |
| 高度粒度 | 0.1 m | `world.diff`(§1) |
| 仿真 tick | 0.1 s(10 Hz 网格/状态同步) | — |
| 块流式半径 | 2(5×5 邻域) | — |
| LOD 近界 | 40 m（距离量到**地块 AABB 的最近点**，非块中心——见下注） | `world.performance.lodNear` |
| 时间历法 | epoch 0 · speed 1.0 · localDaySeconds 600 | 世界文档 `time` 段(`{epoch, speed, localDaySeconds}`) |
| 虚空回收深度 | 20 m | `player.capacity.voidRecover` |

> **距离怎么量(2026-07-27 加,踩坑而来)**:上表凡是「到地块的距离」,一律量到
> **地块 AABB 的最近点**,不是块中心。**块流式半径**同理——窗口是 `(2·半径+1)²`
> 的**方形**,它最远的内容在**对角线**上(角块中心 = `半径·√(块宽²+块长²)`,是正交
> 边的 **√2 倍**)。任何按正交距离裁剪的东西(LOD、雾、剔除)都会**恰好切掉四个角**,
> 鸟瞰下窗口从「田」变成缺角的「井」——参考实现在 LOD 和距离雾上同时踩了这个坑,
> 两处的块**都已加载、仿真照跑,只是看不见**。第二引擎实现时按最近点/对角算。

**客户端观感(桶 C,非规范)**——各实现自定,协议不约束:鼠标/触屏灵敏度、
摇杆死区、相机 FOV/近远裁剪、小地图视锥、相机抖屏/下沉、自动回正速率。
